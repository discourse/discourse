# MCP content restrictions: unit 4 write oracle

Test-only work for the paired build. The implementation belongs to the implementer; this directory never loads or edits the unit 1–3 oracles. Every example contains `[cr-u4]` and drives a registered primitive through `DiscourseMcp::Server` with real OAuth authorizations and persisted records. The baseline is `ae8d882a47743b20498b224189c0b9c876e90bf6`.

The final observed inventory is below. RED means an assertion about the requested behavior failed, after its no-rule calibration succeeded. GREEN entries are explicitly marked **expected GREEN at baseline**, with the reason; they remain regression pins. A GREEN upload acceptance case does not imply grant enforcement exists today: the paired unauthorized-use cases distinguish that permissive baseline from the intended implementation.

Run with the installed Ruby 4 runtime on PATH:

```sh
LOAD_PLUGINS=1 RAILS_DB=discourse_test_mcp_content bin/rspec \
  spec/lib/discourse_mcp/content_restrictions_unit4/
```

[verification.json](verification.json) records the commands, seeds, HEAD, summaries, per-example assertion signatures, source digests and item B receipt. All examples use an administrator except real author recovery, the permission-order counterexample, required-tag-group validation (which admins bypass), and the original uploader in the deduplication fixture. The standard CDN configuration helper sets the asset host; network stubs cover external HTTP/storage boundaries. Guardian methods, policy results, renderer results and egress checks are never stubbed.

## Decisions where the plan left room

1. **One generic reference error, without choosing an implementation key.** Use a real ungranted-avatar-ID refusal as the canonical complete MCP envelope. Every rejected reference, non-standard renderer edit, unsafe stored-raw operation and ungranted profile use must match it. This baseline guard already exists, so existing guards remain GREEN while missing write checks are RED. Deduplication has its explicitly permitted separate generic response; the oracle rejects filename, hash, upload ID and owner disclosures and verifies no ownership row is added.
2. **Content-bearing fields include displayed and subsequently published text.** Besides the listed minimum, pin post edit reasons, category names, group full names/titles, user names/titles/location/website, status descriptions, PM invitation text, moderation reasons and custom signup text/array values. Identity selectors, dates/locales, glyph/style settings and email/domain configuration are not arbitrary rendered content. The live upload-ID arguments usable under active rules are user update/create avatars; profile/card backgrounds use URLs. Theme-setting and nested theme-field upload IDs belong to tools already disabled as exit paths; a grant does not enable those tools. Group flair upload IDs and category permission writes are not exposed by these MCP schemas.
3. **Renderer-inert prose stays allowed.** Version `1.2.3`, filename `garden.txt`, and a URL inside an inline code span are allowed: the current renderer produces no link/media reference from them. Plain prose and labeled external links are checked under forum-only and PM-only rules. URL-valued website/featured-link fields use clearing as their safe control; arbitrary prose would already fail their normal validation.
4. **Use actual surviving URL attributes.** The renderer strips raw `img[srcset]` and agent-supplied `data-download-href`; those were removed as refusal probes after observing the cooked output. Surviving `source[srcset]`, track sources, video posters, onebox source attributes and anchors inside quotes remain. Mixed granted/external srcsets enable the existing `upload` href scheme and omit whitespace after the comma, so both candidates demonstrably survive this renderer. Test both candidate orders and a granted image wrapped in an internal anchor.
5. **PM-only rules still validate ordinary content.** Duplicate authored-field probes under PM-off where the operation remains usable. PM tools, membership requests and custom moderation messages are already refused by PM-off itself, so their reference checks run under a forum rule that permits PMs. Unknown direct/draft/watched tags also have PM-only probes.
6. **Grant identity is the authorization, not its access token or user.** Pin two tokens on one authorization, two authorizations for the same user, uploads outside MCP, another user's upload, and fresh grants issued while rules are active. A later human reference is made through the ordinary platform write path; one case uses the same user as the MCP authorization. Repeated references from this authorization's own written posts stay usable.
7. **Effective tags are checked before storage.** Create/update/move probes expand synonyms and auto-added parents. Watched-word probes cover title and raw, expansion of watched synonyms/parents, and create-only application. An unknown watched replacement is produced by valid configuration followed by deletion of its tag: `WatchedWord` does not accept a nonexistent replacement at configuration time, but the persisted configuration can become stale.
8. **Error wording.** For required-tag-group, mutually exclusive-tag and required-custom-field validation, choose the plan's exact generic fallback; no new static safe translation is prescribed for those cases. Duplicate titles may instead use the plan's proposed `This title is already used`. Preserve an existing content-free `mcp.errors.*` confirmation message. Populated-category deletion already fails with a content-free 403 before native content-bearing deletion reasons are produced; retain that real behavior rather than bypassing Guardian to manufacture an error.
9. **Draft backup suppression means no new/updated backup.** Existing human/platform backups are left unchanged, consistent with `Draft.set(backup: false)`; this is not a purge requirement. The forum-rule case checks no backup topic/post is created, and the PM-only case checks an existing copy remains byte-for-byte unchanged.
10. **Queued revise and unhide use real actions.** The reachable revise action is `revise_and_reject_post`; no `additional_fields` are supplied because those are already blocked under an active rule. Both ReviewablePost approval/unhide/restore and flagged-post disagreement/unhide are covered. Safe stored raw remains usable. Restricted own-post deletion and recovery compare missing responses for an admin and a member whose normal operation is forbidden, proving the policy answer precedes permission checks.
11. **Independent receipts justify generated examples.** Matrix cells are separate examples, as in unit 2, so every field/form has its own RED signature. Narrow linter exceptions retain that required attribution; all other Ruby lint checks apply. The only fixed missing ID is `93_400_999`; real record IDs are fabricated and no units 1–3 fixed range is reused.
12. **Scope is the user's scope.** Configured responders, AI bots, automations and workflows are not exercised. Human/platform copying itself is not prohibited or tested; human writes appear only as fixtures for the explicitly requested live grant-revocation and stored-raw cases.

## Needs non-test gates

- **Validation must not resolve/enrich candidates.** Code review must verify that validation does not call enrichment or resolve targets, and that its renderer options/tokens remain independent of linkify/onebox settings. Calling a cache-only enrichment function can have no observable MCP/state effect; mocking its invocation would violate this oracle's interface boundary. Settings-independent rejection itself is tested.
- **Typed error provenance.** The response tests prove the selected real validation failures are content-free and the known safe confirmation survives. They cannot establish that implementation dispatches on error keys/types rather than scanning text: identical wire strings do not expose that provenance. Review the allowlist and its interpolation rules.
- **Implementation inventory completeness.** Review the shared field/cooking-operation inventory against the live schemas and call graph, and require future tools/plugins/renderers to join it. Tests deliberately do not name a future constant, helper, grant table or schema layout. Also review newly allowed renderer attributes: currently stripped `img[srcset]`/`data-download-href` cannot be separately exercised as surviving references today. Runtime bot/workflow coverage is excluded by user decision, not an outstanding gate.

## Plan fault found

The literal instruction to validate with `Post#cook` while not calling `Oneboxer.apply` conflicts with the current call graph: `Post#cook` delegates to `PostAnalyzer#cook`, which invokes `Oneboxer.apply` after rendering. `PrettyText` exposes `onebox_limit`, feature and markdown-rule options, but that does not itself give an enrichment-free `Post#cook` API. The implementer must reconcile the real-renderer requirement with a candidate-only validation pass. No framework or renderer implementation was changed for the oracle.

The accepted unit 2 corrections are retained: UpdateTopic schedules processing of stored raw, unhide itself is not an unconditional rebake, group saves cook unchanged bios, and historical recovery can replace current raw. Category description updates cook the newly submitted description into the definition post; the oracle does not claim a category rename recooks its old description.
