# Workflow AI authoring use cases

Purpose: maintain a durable set of prompts for evaluating the Workflow AI authoring loop as schemas, tools, and prompting change.

## How to run a dev eval

Use the synchronous dev runner so the latest local code and tools are used:

```bash
bin/rails runner /tmp/workflow_ai_dev_run.rb '<prompt>' 'AI dev eval <id>' > /tmp/workflow_ai_<id>.json
```

For each run, record:

- Session/workflow IDs and status
- Tool calls used
- Proposal shape
- Whether Code nodes were avoided when declarative nodes are sufficient
- Whether `workflow_validate_patch` was used and final `expression_errors` is empty
- Token/time totals
- Any optimization applied

## Known edge cases to keep testing

- `action:topic_tags` version `2.0` defaults to `mode: modify`: `add_tag_names` and `remove_tag_names` apply together, preserving unrelated tags and allowing implicit parent tags. `mode: replace` sets the complete tag set from `replace_tag_names`; an empty value clears all tags. Replacement uses the current topic state under a lock and rejects category or parent-tag rules that change the requested final set. Only the selected mode's fields are evaluated; invalid names and expression errors stop the action before any tag changes. Both modes enforce the actor’s permission to edit the topic’s tags and return the final `tag_names`; rejected changes neither persist nor emit tag-change events. Existing tag names remain usable after the maximum tag length is reduced. Version `1.0` retains `operation` and `tag_names`.
- Topic timer triggers are separate nodes: `trigger:topic_timer_set` (created or rescheduled, with `change`, `timer` and `previous_timer`), `trigger:topic_timer_cleared` and `trigger:topic_timer_completed` (with `timer`). Their timer-type filter matches either the previous or current type, so replacing a publication timer with a close timer still matches a publication filter; inspect `timer.status_type`. Every reply to a topic with a timer based on the last post, and every scheduled run deleting replies, fires Topic timer set; deleting replies never completes. They ignore private timers: slow mode's end has its own triggers (only the hidden `trigger:topic_timer_changed` still sees it). The existing `trigger:topic_timer_changed` remains editable and executable but is hidden from the picker and AI discovery. A workflow that sets a timer from Topic timer set reschedules on every run and triggers itself.
- `action:set_topic_timer` replaces the topic's single timer (`changed` is false when it already had that exact timer); `action:clear_topic_timer` cancels the timer of one type and leaves others alone. Only close timers can be based on the last post: replies reschedule such a timer as a close timer.
- `trigger:topic_published` and completed publication timers expose the topic in its destination category. Use the topic timer triggers for scheduling and cancellation, and `trigger:topic_published` for publication cleanup.
- `action:set_slow_mode` (an interval with a unit, optionally until a time) and `action:clear_slow_mode` go through the same service as the topic's slow mode modal, so only staff and trust level 4 actors can use them. Leaving the end time empty removes one set earlier. `trigger:topic_slow_mode_set` fires when slow mode is turned on or its interval or end time changes, and `trigger:topic_slow_mode_cleared` when it's turned off, including on expiry (as the system user); saving the same slow mode again fires neither. Slow mode turned on by a category's default slow mode, when a topic is created in or moved to that category, fires no trigger.
- `action:convert_to_personal_message` and `action:convert_to_public_topic` (optionally into a category; empty uses Uncategorized, or the first public category) go through the same converter as the topic's admin menu, so only staff can use them, and the acting user becomes a participant of the personal message. They report `changed: false` when the topic is already in that form, and refuse to convert the banner. `trigger:topic_converted_to_personal_message` (tag filter only, since the message has no category) and `trigger:topic_converted_to_public_topic` (category and tag filters) fire for every successful conversion, including bulk actions and personal messages published to a category on a schedule (as the timer's user). Conversions also fire `trigger:post_edited`, because they revise the first post.
- `action:topic` 2.0 `delete` and `recover` go through the topic's first post like the topic's delete and recover buttons (`changed: false` when it was already in that state). `trigger:topic_deleted` fires once each time a topic goes to the trash, whoever or whatever deleted it (timers as the timer's user, merges as the merging user, workflow actions, category deletion without an actor); a topic its author deleted only fires it once the topic is actually removed, as the system user. `trigger:topic_recovered` fires when a deleted topic is restored, not when authors cancel their own pending deletion. Both expose `$json.actor` (who acted) and `$json.user` (the topic's author). Deleting a first post fires both `trigger:post_destroyed` and `trigger:topic_deleted`, so use one of them per workflow. Workflow actions skip `trigger:post_destroyed` and `trigger:post_recovered` but still fire Topic deleted and Topic recovered, so a workflow recovering topics on Topic deleted and another deleting them on Topic recovered would loop.
- Topic status triggers are separate nodes: `topic_closed`, `topic_reopened`, `topic_archived`, `topic_unarchived`, `topic_listed`, `topic_unlisted`, `topic_pinned`, `topic_unpinned`, `topic_pinned_globally`, and `topic_unpinned_globally` (all prefixed with `trigger:`). They share category and tag filters. Closing includes automatic closes; unpin events use the previous pin scope, and expiring pins fire them as the system user. Workflow and AI actions use the same status updater. `trigger:topic_bannered` and `trigger:topic_unbannered` fire when a topic becomes or stops being the banner, including when a new banner replaces it or the banner expires.
- Review outcome triggers are `trigger:reviewable_approved`, `trigger:reviewable_rejected`, `trigger:reviewable_ignored`, `trigger:reviewable_deleted`, and `trigger:reviewable_pending`. They share the reviewable-type filter. Pending handles an existing item returning to review; use `trigger:reviewable_created` for new items.
- Connect multiple event triggers to the same downstream node to handle several events. Existing `trigger:topic_status_changed`, `trigger:reviewable_status_changed`, `trigger:post_like_changed` and `trigger:user_moderation_changed` nodes remain editable and executable, but are hidden from the picker and AI discovery. Fixed-event nodes have no status or change selector and ignore any supplied `statuses` or `changes` configuration.
- `trigger:user_trust_level_changed` exposes old and new levels, including demotions. `trigger:user_first_logged_in` follows the first-login event, whose first-visit check uses `last_seen_at`.
- `trigger:user_suspended`, `trigger:user_unsuspended`, `trigger:user_silenced` and `trigger:user_unsilenced` fire once each time a penalty is applied or ends, with `$json.user` the affected account and `$json.actor` whoever acted. User suspended and User silenced also have `reason`, `message`, `post_id` and `expires_at` (around the year 3026 for a penalty "forever", which core counts as anything over 100 years); User unsuspended and User unsilenced only have `user` and `actor`. Bots and the system user never fire them as the affected account. The hidden `trigger:user_moderation_changed` keeps firing for all four with its `change` key. Workflow runs are enqueued after commit, so a penalty applied inside a review queue action that rolls back starts none.
- Who `$json.actor` is: staff on the admin user page (one run per account, including the other accounts picked in the suspend or silence modal) and its unsuspend and unsilence buttons; the reviewer for review queue penalties and unsilences (flagged posts, queued posts, users, chat messages, post voting comments, live users, AI posts and chat messages), who may be a category moderator that isn't staff when approving a queued post, which unsilences its author whatever the silence was for; the approving moderator for the AI suspend and silence tools; the AI agent's user, or the chat user approving it, for AI review actions; the automation script's actor, or the system user, for suspending by email; the system user for automatic silences (flag thresholds, Flag post `spam_silence`, typing too fast, watched words, spam email headers, chat rate limits and flags, post voting flags, AI triage and the AI flag tool); the AI spam scanner's flagging user; and the node's actor for Flag post `review_delete_silence` and the four actions below.
- A suspension ends at its exact time, as the system user, through a job scheduled when it was applied. Suspensions applied before that job existed, or whose job was lost (a Redis flush, a restore from a backup), never fire User unsuspended on their own, and nothing sweeps them up. If server clocks disagree and the job runs before the end, it does nothing. A silence is lifted, as the system user, up to 15 minutes after its end; unsilencing it before then reports whoever unsilenced it. Unsuspending a suspension whose end was already reported does nothing (no staff log, no event, the dates are kept); one that ended without being reported ends now, reported once as whoever unsuspended it.
- Penalties don't always alternate with their ends: a silence past its end that hasn't been lifted yet, or a suspension in the seconds before its expiry job runs, can be applied again, firing User silenced or User suspended twice in a row, and two concurrent suspensions (or silences) of the same user both apply and both fire.
- Anonymous accounts: silencing the anonymous account someone posted with (automatic silences of an anonymous post, Flag post, AI tools, Silence user) silences the account behind it, but `$json.user` is the anonymous account, so nothing links the two; when that silence ends on its own, User unsilenced reports the account behind it, as the system user. Suspending an anonymous account suspends only that account, and copying an account's suspension to its anonymous accounts fires nothing.
- `action:suspend_user`, `action:silence_user`, `action:unsuspend_user` and `action:unsilence_user` are for staff actors only, like the admin user page: any other actor fails, even when nothing would change. Staff can't be suspended or silenced, and only admins can unsuspend or unsilence staff. Suspend user and Silence user go through the admin modals' service (staff log, the email with the optional message, and Silence user's system message), one user per item and without the modal's other accounts or post actions (use the Post node). The penalty ends after a `duration` (hours to years, at most 1000 years, which core treats as forever) or at a future `suspended_till` / `silenced_till` in the node's timezone, and `post_id` may be a deleted post. They output `user`, `actor`, `changed` and `expires_at` (the key the triggers use, rather than the setting's name); `changed: false` means the user already had that penalty, which is kept with its end (lift it first to change it). Silence user keeps the user's posts visible, like the admin modal and unlike Flag post `spam_silence` and automatic silences, which hide a new user's last day of posts. Unsuspend user and Unsilence user go through the admin buttons and output `user`, `actor` and `changed`; Unsilence user sends the user a system message, Unsuspend user nothing. These actions fire the triggers above, so a workflow suspending on User unsuspended and another unsuspending on User suspended would loop.
- `trigger:solution_changed` is available with Solved and reports acceptance or removal of an individual answer. Removing one answer can leave other accepted solutions; replacing an answer emits acceptance for its replacement.
- Topic-only triggers expose the author as `$json.topic.username`; use `action:topic` get only when first-post fields are needed.
- Generic prompts like "when someone posts" should use `trigger:post_created` for all regular posts; do not ask whether to include replies unless the prompt explicitly narrows the scope.
- Actions that replace item JSON require downstream nodes to use the action output schema, not the original trigger schema.
- Dynamic strings containing `{{ }}` must start with `=`.
- Simple trust/text/category/staff checks should use `condition:filter`, not Code nodes. `condition:if` is for separate true/false branches.
- Trust level is only exposed as `$json.user.trust_level` on triggers with a user object (e.g. `trigger:post_created`); the post/topic payloads have no `trust_level`. When a trust-level check is needed but no `trust_level` field is in scope (topic-only triggers), resolve the cumulative `trust_level_N` automatic group and use `action:group` with `operation: check_membership` plus resolved `group_id` -- do not ask for clarification or add a Code node.
- Condition builder entries must use `leftValue` and `rightValue`; `left`/`right` will not execute correctly.
- Connections leaving `condition:filter` or `condition:if` use `connection_type: "main"`; select the passing branch with `output_index: 0` and the rejected branch with `output_index: 1`.
- Group membership checks should use `action:group` with `operation: check_membership` and the resolved `group_id` instead of Code nodes. Branch with `condition:if` on `$json.group_membership.in_group` when different member and non-member paths are needed.
- Deleting a post is `action:post` with `operation: delete`; `action:flag_post` with `review_delete` is for moderation flows that also need a reviewable. Restoring one is `operation: recover`.
- Flag post reasons and Flag user notes name the nearest AI Agent on the item's executed input path. Conditions preserve that attribution; merged inputs from different Agents or incomplete item links retain Workflow-only attribution. Successful flags persist the attributed Agent ID in a dedicated reviewable-to-agent table, making that Agent available in the Review Queue Reason filter without parsing reviewable content. Agent filtering survives renames and preserves Workflow filtering and score deduplication. Ambiguous or skipped flags do not add an Agent. Existing payload attribution is backfilled only for reviewables with Workflow score provenance; historical data does not establish individual Workflow–Agent pairings. 
- `action:like_post` and `action:unlike_post` go through the like button's creator and destroyer, so they follow its rules: no liking your own post, as a silenced user or in an archived topic, and Like post notifies the author like the button does. Unlike post only removes the actor's own like, within `post_undo_action_window_mins` (10 minutes by default), and fails afterwards. Both report `changed: false` when the actor had already liked, or not liked, the post, which only needs the actor to see it. Like the button, Unlike post doesn't check that the actor can still see the post when it removes a like; its output is only visible to workflow managers. Deleted posts raise not found for both, even for staff actors (deleting a post already removes its likes).
- `trigger:post_liked` and `trigger:post_unliked` (category, tag and topic filters) fire for every like given or taken back: the like button, likes by email, workflow actions, discobot, and reactions that count as likes (switching reaction fires Post unliked then Post liked). `$json.user` is the post's author and `$json.actor` whoever liked or unliked, so whenever a post changes owner (staff in the topic menu, user merges, embed imports, rake tasks) and the new owner's like is removed, Post unliked reports the new owner as actor. Neither fires when a post or user is deleted, when users are merged (their likes move in bulk) or for bulk like removals (reaction like syncing, the `posts:delete_all_likes` task). Like post and Unlike post fire them too, so a workflow unliking on Post liked and another liking on Post unliked would loop.
- `action:hide_post` and `action:unhide_post` are for staff actors only, like taking action on a flag and the post's unhide button: any other actor fails, even when the post is already in that state (`changed: false`). Like the post menu, they also work on deleted posts and posts in deleted topics. Hide post hides the post the way flags do, sending its author the hidden-post message with the chosen `flag_reason`; it doesn't add a review queue item (use `action:flag_post` with `review_hide` for that). A post hidden for the first time has `hidden_reason` `flag_threshold_reached`, so its author can unhide it by editing it after `cooldown_minutes_after_hiding_posts`; a post hidden before gets `flag_threshold_reached_again`, which an edit doesn't undo. Hiding a topic's first post (or its last visible post) unlists the topic, and unhiding a first post that unlisted it lists the topic again. Both output `post`, `actor` and `changed`.
- `trigger:post_hidden` and `trigger:post_unhidden` (topic type, category, tag and topic filters) fire for regular posts only, once each time a post really is hidden or made visible again, with `$json.user` the post's author, `$json.actor` whoever acted, and `$json.hidden_reason` (why it is, or was, hidden). Post hidden also has `$json.flag_reason` (such as `spam` or `inappropriate`), null when no flag was involved. The actor is the system user when flags reach the hiding threshold, when a trust level 3 user's spam flag hides a new user's post, and for AI triage and the AI flag tool; staff for take action and flag-and-queue; the reviewer for review queue actions; the AI spam scanner's flagging user; the silencing user (the system user for automatic silences) when silencing a new user hides their last day of posts; staff using the unhide button or removing a flag they took action on; and the author when they edit a post hidden by flags, in which case Post unhidden fires before Post edited. Posts created already hidden (spam email headers, imports) and hidden revisions never fire Post hidden. Topic unlisted and Topic listed report the system user when hiding or unhiding changes the topic's visibility, except on flag-and-queue of a first post, where the flagging staff member unlists the topic first; silencing a new user unlists their topics without firing Topic unlisted. Hide post and Unhide post fire these triggers too, so a workflow unhiding on Post hidden and another hiding on Post unhidden would loop.
- `action:lock_post` and `action:unlock_post` go through the post admin menu's lock, so they are for staff actors only (any other actor fails, even when the post is already in that state) and write the post_locked / post_unlocked staff log. Like the post menu, they also work on deleted posts and posts in deleted topics, but not on personal messages the actor can't see. Both output `post`, `actor` and `changed`; `changed: false` means the post was already locked, or already unlocked, and then nothing is logged and no trigger fires (an already locked post keeps who locked it).
- `trigger:post_locked` and `trigger:post_unlocked` (topic type, category, tag and topic filters) fire for regular posts only, once each time a post really is locked or unlocked, with `$json.user` the post's author and `$json.actor` whoever locked or unlocked it: staff from the post menu, workflows, and AI tools (as the AI bot user, also when a moderator approved the action). With `staff_edit_locks_post` on, a staff edit (other than by the system user) of a non-wiki post by a non-staff author locks it, and fires Post locked as the editor, before Post edited (after it when the edit runs inside a larger transaction, such as approving an AI tool's edit). That counts any edit that sends the post body, even unchanged, so a staff title, category or tag change from the composer locks a member's first post; so does a staff member ticking a checklist box in a member's post, reverting a revision's body, or an AI tool editing a post. Later staff edits of the locked post fire nothing, nor does locking a post someone else already locked. Workflows editing a post with the Post node skip Post edited but still fire Post locked when a staff actor's edit locks it. Merging users moves who locked a post without firing anything. Lock post and Unlock post fire these triggers too, so a workflow unlocking on Post locked and another locking on Post unlocked would loop.
- `trigger:post_destroyed` and `trigger:post_recovered` expose the post author as `$json.user` and whoever deleted or restored it as `$json.actor`.
- `$json.user` is the subject (author, affected account) and `$json.actor` whoever acted. Version `2.0` of `trigger:post_edited` (`editor` → `actor`), `trigger:post_like_changed`, `trigger:post_reaction_changed`, `trigger:topic_received_vote` (liker/reactor/voter → `actor`), `trigger:card_moved` (`acting_user` → `actor`), `trigger:assigned`/`trigger:unassigned` (`assignment.assigned_by_user` → `assignment.assigned_by`) and `action:post_like` (`username` → `actor`) apply this; version `1.0` keeps the old keys and is deprecated. `action:post_like` is now deprecated at both versions, replaced by `action:like_post` and `action:unlike_post` (output `post`, `actor` and `changed`; `post_id` becomes `post.id`).
- DM/personal-message notifications should use `action:send_personal_message` instead of chat or topic reply nodes. Only an explicit chat DM uses `action:send_chat_message` with `target: "user"` (or `"group"` for one group DM).
- Forum `search`/`read` should not be used for node/schema discovery; use `workflow_node_catalog` and `workflow_validate_patch`.

## Moderation entrypoints

Live suspensions from admin actions (single and bulk), AI tools, and automation use `UserSuspender`. Manual unsuspension and scheduled expiry use the same class. Expiry preserves historical suspension dates and deduplicates its event through staff history; clearing those dates would change badge eligibility.

`UserSilencer` already handles admin, review queue, spam, chat, AI, and workflow silence actions, manual unsilencing, and scheduled unsilencing. No additional silence service is needed.

Direct field writes intentionally remain in historical imports, anonymous shadow-account synchronization, and AI bot self-repair. These restore or copy state rather than perform independent human moderation actions, so they must not send moderation messages or create duplicate workflow events.
