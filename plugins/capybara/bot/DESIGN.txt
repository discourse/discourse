The board is the request authority. A topic-backed card supplies title, latest body, replies and upload images. TODO creates a fresh isolated checkout of the committed capybara branch. BACKLOG has no trigger.

The controller owns Run records in SQLite. New records carry integration_version=1; legacy records deserialize to zero. running -> review -> integrating -> deploying -> publishing -> confirming -> done is the accepted path. Failed integration remains visible and does not acknowledge success. New runs require publication; legacy saved runs default to publication_required=false.

A trusted integration container receives read-only card workspace and writable source checkout. Its coding conflict resolver runs with write access restricted to its isolated integration checkout. It applies base..head changes onto current capybara, commits with a stable run marker, fetches official discourse/discourse main and rebases local commits onto that pinned SHA. Publication checks a clean capybara checkout, uses a compare-and-swap branch update and non-destructive read-tree checkout, and saves backup and per-run refs. Local integration has no remote credential.

DockerBoard(config, client).deploy(commit, event) stops the prior board container, recreates it with the selected source commit and persistent database, uploads, Redis and Linux workspace, installs bundle and pnpm dependencies, migrates, starts frontend and Rails, checks public frontend and administrator login. reconcile() runs before polling the board so restart can proceed during board downtime.

A native host helper was considered. It would need another durable queue and native dependency/process supervision. The Docker runtime keeps these operations in the existing controller and follows the user's all-Docker requirement. The one-time native database dump and original native database remain as rollback records.

ForkPublisher owns a separate durable publication journal with the immutable repository ID, capybara ref, upstream main and PR number. Before each push, the trusted helper validates fork identity, PR head/base and open state. An explicit refspec and force-with-lease compare the recorded remote SHA, while the pending SHA lets retries recognize an already completed push.
The helper saves an accepted receipt immediately after Git accepts the push, before PR metadata confirmation.
The controller recovers receipts and attempt diagnostics from a previous publisher before removing it and saves acceptance in its durable journal.
Accepted runs enter confirming. Subsequent attempts read the exact GitHub ref and PR identity without any Git import or push.
Stale PR metadata, API failures, and a changed remote head remain distinct diagnostics. A changed head is never overwritten after acceptance.
Per-run JSONL attempts, structured helper results and bounded process output survive container cleanup with credentials redacted. Unknown remote changes stop publication. Only successful deployment and publication allow the topic DONE acknowledgement and next TODO claim.

The fine-grained Contents write token is limited to discourse/capybara-bot and stored outside all coding mounts. Only the controller and its dedicated disposable publisher receive it. The publisher gets a read-only seed and private root-only secret files, without Docker socket or Codex credentials. Cleanup removes the secret and container. The coding sandbox cannot access the credential; host Docker administrators remain trusted. Publisher helpers and images are installed by the operator rather than rebuilt from card changes.

Capybara card deletion uses the existing Boards deletion permission checks, then closes an open topic and deletes its card in one transaction. Open topics require close permission. Closed topics stay closed without another status post. This extension runs only in development on the configured board. Missing cards already cancel running/review jobs with durable cleanup retries. Accepted integration phases continue to publication to avoid stranding a changed local branch or pending remote journal.

The main tunnel has HTTP Basic authentication configured from an external controller-only secret. Origin-scoped clients protect polling and deployment checks without sharing credentials with coding or preview instances. Reconciliation tests anonymous and authenticated access before deciding whether the main tunnel needs replacement.

Run volume retention
--------------------
Each successful board poll reconciles recorded workspace, integration, and session volumes. Running and REVIEW attempts, every integration/deployment/publication/confirmation phase, and unfinished background jobs retain their volumes. The current failed attempt retains its workspace for diagnosis and export until it is superseded, deleted, or moved to DONE. An integration failure retains its accepted work even in DONE until it is superseded or deleted. Shared sessions and legacy workspaces remain while any recoverable attempt references them.

Completed, deleted, cancelled, and superseded attempts release their volumes once container cleanup and background jobs finish. Completed/deleted/superseded workspaces can no longer be exported after reclamation. Publication diagnostics and run metadata remain in controller state. Ownership labels must match this board and card; unknown volumes and volumes attached to any running or stopped container are untouched. Docker conflicts and temporary API errors are logged and retried on later polls. No global volume prune is used. The main board database, Redis, uploads, workspace, and controller state are retained. A failed board snapshot cannot authorize volume deletion.

Main board login persistence

The main Redis volume mounts at /shared/redis_data, matching the worker image's Redis data directory. Before Rails starts, board-secret.py atomically persists its 128-hex application secret in /workspace/board-secret-key-base with mode 0600, and board.sh exports it as DISCOURSE_SECRET_KEY_BASE. The existing valid Redis SECRET_TOKEN is adopted on first initialization. Later restarts reuse the saved key even if Redis loses cached data, so application cookie encryption and auth-token digests stay stable. An invalid saved file stops startup rather than rotating the key.

When upgrading an existing board without this file, preserve its current Redis SECRET_TOKEN in that path before replacing the container. The previous Redis mount did not cover its actual data directory, so replacing first would discard the key and invalidate existing logins once more. Keep this file private and preserve the main workspace volume.
