# Flaggable user profiles

Enable **Flaggable user profiles** under Admin → Upcoming changes for the members who should be able to report profiles. Eligible members see **Flag** on another user's full profile, including accounts that have never posted. The profile must be visible to the reporter. The usual flagging group, staff-target and daily limit settings apply. Members can select an enabled reason, including a custom flag assigned to user profiles. [Profile permissions](../lib/guardian/user_guardian.rb) · [Flag submission](../app/services/user/flag_profile.rb)

Selecting **It’s Illegal** requires an explanation and confirmation. When **Allow all users to flag illegal content** is enabled, members in the rollout can select this reason even if they are silenced or outside the usual flagging groups. When DSA reporting is enabled, the same choice opens the dedicated notice form with the profile URL already filled in. Members can submit a DSA notice even if they already have a pending profile flag. [DSA notice form](../frontend/discourse/app/components/dsa-notice-form.gjs)

Visitors included in the rollout see **Flag** on eligible public profiles when anonymous illegal-content reporting is available. This includes public staff profiles on sites that disable ordinary flags against staff. With DSA reporting enabled, the button opens the notice form with the profile URL filled in and asks the visitor to verify their email. Otherwise, **Allow all users to flag illegal content** opens an email link to the site's illegal-content reporting address, falling back to the site contact address. The email includes the profile URL.

## How moderators review a profile

A **Flagged profile** item shows the username, public profile details, avatar, profile header, and user card background captured when the first pending report was submitted, plus a link to the current profile. Other members' reports join that item. Each reporter contributes one pending flag. When a resolved profile is reported again, the queue captures its current details. The review question and reason badges use flags from this reporting cycle. Earlier flags remain in the timeline. [Reviewable model](../app/models/reviewable_flagged_profile.rb)

The review queue asks a question based on the flag reason, such as **Is this profile spam?** Under **Yes**, moderators can keep the profile, remove profile content, silence the user, or suspend the user when their permissions allow it. **Remove profile content** asks for confirmation, then clears the current bio, website, profile header, user card background, and public profile fields and resets the avatar to the default. This includes edits made after the report. The member keeps their name, title, and location. The queue retains the snapshot and records who removed the content. Under **No**, **Dismiss flag** records a disagreement with the report, while **Ignore** closes it without taking a side. Moderators can still resolve existing reports after the upcoming change is disabled. Expired reports are marked ignored. [Review actions](../app/models/reviewable_flagged_profile.rb) · [Queue cleanup](../app/jobs/scheduled/auto_queue_handler.rb)

When **Blur TL0 flagged posts media** is enabled, the queue also blurs the avatar image captured in a trust-level-0 profile report. Hover over the image to reveal it. [Review queue image styles](../app/assets/stylesheets/common/base/reviewables.scss)

Profile reports use `ReviewableFlaggedProfile` with a `UserProfile` target. Account approval and suspect-account reviews use `ReviewableUser`, whose expiry action can delete an account. Keeping these decisions on separate queue items lets a moderator review a profile without reopening its signup decision. [Account reviews](../app/models/reviewable_user.rb) · [Regression specs](../spec/requests/user_profile_flags_controller_spec.rb)

Deleting or anonymizing the account clears the saved profile and releases the report’s references to uploaded images. Review-note mention notifications use **Flagged profile** as their title in each recipient’s interface language, including for former moderators. A pending report closes as **Ignored** with a note explaining why. A resolved report keeps its original decision. [Account deletion specs](../spec/services/user_destroyer_spec.rb) · [Anonymization specs](../spec/services/user_anonymizer_spec.rb)

Deleting a reporter removes their pending flags. A report with another pending flag stays open. When the last reporter is deleted, a report retained for another member’s review history or a pending DSA statement closes as **Ignored** if it was still open. Deleting the account from a queued post also removes closed reports from open pending queues. Staff can finish classifying the statement. Deleting a report releases its retained media.

## Review suggestions and DSA

A new profile report enters the shared action-suggestion flow when a decision model is configured and suggestions are enabled. The model receives selected snapshot text, the flag reasons and the available actions. Moderators can apply a suggestion through the usual review controls. Reopening a report discards the previous suggestion. The next suggestion uses the fresh snapshot and the currently pending profile flags. For flagged posts and other queue items, the model receives the full flag history.

When DSA reporting is enabled, the removal dialog explains which current content will be cleared, including later edits. Removing visible text or images records a visibility restriction dated using the most recent item removed. Empty fields and unchecked confirmations contribute neither a restriction nor a date. Images use their upload dates and public fields use the dates of their values. The bio and website use the profile’s creation date because those fields have no separate timestamp. A new reporting cycle uses its own illegal-content status for classification. Silencing or suspending the profile owner records a statement for the account restriction. A separately configured classification model can suggest a community rule and category for the moderator to confirm. Profile classification uses the captured name, biography, website and flag reasons from the current reporting cycle as evidence. Avatar images, profile headers, user card backgrounds and custom profile fields are outside the model input.
