Enable `dsa_reporting_enabled` to retain restrictions applied through the review queue. It is disabled by default. Handling and queue visibility remain unchanged. This phase adds no classification UI, notes, submission jobs or Reviewable fields.

## Stored records

`dsa_statement_of_records` contains only `id` (UUID), `reviewable_id`, `status`, `payload`, `created_at` and `updated_at`. The row UUID is also its payload `puid`. There is no API response identifier or private evidence column.

Only the first handling decision is recorded. Reopening, later decisions and reversals are outside this iteration. A first decision that opens a penalty dialog creates no restriction until the later request applies it. Background user deletion can also complete that first decision later.

`payload` is the draft public SoR request body. It contains reliably known restrictions, dates, content types, territorial scope, initiating source and separate detection and decision automation. Classification must later supply facts, grounds, category and the conditional explanation. Neither a flag nor an approval establishes a legal or terms conclusion.

Compatible effects on the same recipient and content date within the first handling decision share a payload. For example, deleting an author and their post can produce one payload containing both account termination and content removal. Different recipients or content dates require separate payloads because the API has a single content date and each decision describes its recipient. Later requests and background batches may create additional payloads for restrictions applied separately. All related rows share `reviewable_id`, allowing one future classification form per reviewable.

Classification reuses existing reviewable payloads, scores, histories, revisions and retained targets. There is no default copy of their contents. Permanent deletion can erase target content and scrub staff logs. Retention of those concrete cases is being assessed separately from this recording checkpoint.

## Sources and action mapping

`Reviewable#perform` establishes one context for attribution, grouping and original content metadata. Ordinary moderation record events provide the main inputs. A history status alone is insufficient: approving a flag can keep, hide or remove content. Actual retained state or a restriction record is required.

## Remaining integrations

Post hiding, publication rejection and plugin trashing lack a complete ordinary restriction history. Their existing transition or state events are retained as small integrations inside the common handling context. Topic status events identify actual close and unlist effects, including delegated tools.

Deferred user deletion propagates the original row UUID to the chat deletion job. Bounded batches record actual removals when messages are permanently deleted. Repeating a completed deletion creates no new rows. Post voting comments need the same actual removal integration because their ordinary rows disappear.

Explicit automation provenance remains necessary when an AI decision uses a staff actor. An ordinary staff API or MCP action is still human; actor identity alone cannot distinguish these cases.

Illegal notice intake, authority orders, appeals, moderation outside the queue, annual reporting and delivery are separate work. Future submission must validate the completed [Commission API schema](https://transparency.dsa.ec.europa.eu/page/api-documentation).
